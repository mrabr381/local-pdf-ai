How it works

~600-char chunks 100-char overlap TF-IDF + cosine 0 network calls for search

The JavaScript in app.js is a direct port of the Python backend: localpdfai/chunking.py (chunks never cross a page boundary, so every citation points at exactly one page), localpdfai/embeddings.py (same stopword list, idf = ln((n+1)/(df+1)) + 1, log-scaled term frequency, L2-normalised rows) and localpdfai/index.py (cosine search, ties broken by chunk order — the same question always returns the same passages). Answers are extractive: quoted passages with [p. N] citations and relevance scores. Nothing is invented — and nothing is summarised either; generative answers need the optional local Ollama model in the Python tool.

On the built-in sample the browser search reproduces the Python results exactly: 4 pages, 7 chunks, 6/6 questions top-1 correct (see the full fixture transcript). For an uploaded PDF the numbers can differ slightly from the CLI, because PDF.js and pypdf extract text a little differently — the ranking method is identical.

Honest limitations

  • Extractive answers quote the document — accurate, but they don't summarise.
  • TF-IDF matches on words, not meaning. Ask in the document's own words for the best matches; the Python tool has an opt-in semantic backend (--backend st) that this static demo can't ship.
  • Uploading needs the PDF.js CDN (internet). The built-in sample needs no network at all.
  • Very large PDFs are indexed in memory, in your browser tab — a 500-page PDF will take a while on first index, same as the Python tool.

Local PDF AI on GitHub — MIT licensed. Prefer the command line? pip install -r requirements.txt, then python -m localpdfai ask --pdf your.pdf --q "your question". Measured results on a real document: sample Q&A page.
